# Custody accounting evidence

The default-feature records must measure the production custody representation, independently of the
`.custom-std.num-bigint` projection. A matching toolchain header does not make those feature
projections interchangeable.

The affected mechanisms are:

- Scope initialization stores `Dispatch::owner` alongside the terminal function
  (`src/bounded/decode/construction/reclamation/owned.rs`). The scope contract derives its
  allocation and initialization writes from the concrete block and field sizes. The default-feature
  witness reports 112 allocated bytes and 128 initialization bytes, replacing 88 and 104; its four
  admitted values remain unchanged.
- Text normalization retains its output owner and acquisition capability in `TextContinuation`
  (`src/bounded/text_cursor.rs`). Retained parsing prices initialization through
  `initialization::fields::<TextContinuation<…>>` (`src/bounded/decode/cursor.rs`). String decoding
  and preparation compose that same continuation cost. Initialization writes and their composed
  bounds must therefore be recorded with the current custody layout.
- Preparation retains two whole-element window custody parts per cursor. The preparation bound in
  `src/bounded/encoding.rs` prices their arena using `size_of::<WindowPart<O>>()`, including growth
  rounding, alongside the cursor arena. Cursor storage, initialization, cleanup, and composed run
  bounds include those parts, including empty entry pairs.
- Owned lifecycle bounds compose scope, parse, construction, and preparation costs. Their records
  must be regenerated by the lifecycle attribution witness, including records checked after the
  scope record.

Record values come from executing the attribution witnesses. Preserve each row's outcome and
evidence class; a passing recording run alone does not establish agreement with the compiled-in
records. Rebuild and run with `DCBOR_RECORD_FACTORS` unset to verify that agreement. No ratio is
copied from another feature projection.
